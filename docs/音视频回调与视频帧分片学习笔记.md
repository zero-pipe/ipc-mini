# 音视频回调与视频帧分片学习笔记

本文专门整理 `zero-mini` 中音视频回调、编码帧边界、VENC Pack、NALU、`MediaFrame` 和 RTP 分片之间的关系。

这几个概念属于不同层次，如果混在一起，很容易产生下面几种误解：

- 一次回调是否同时包含音频和视频？
- 一次视频回调是否一定对应一帧？
- I 帧很大时是否会触发多次业务回调？
- `ot_venc_pack` 是否就是一帧？
- NALU、编码帧和 RTP 包是不是同一个边界？

先给出最重要的结论：

> 当前项目的视频回调按编码帧对齐。一次视频回调通常对应一张完整编码图像，但这张图像内部可以包含多个 VENC Pack 和多个 NALU；发送到网络时，一个大 NALU 还可能继续拆成多个 RTP 包。

---

## 1. 音频和视频是否在同一次回调中出现

不会。

同一个 `stream_id` 可以同时包含：

```text
stream_id = 1
  |-- Video Track：H.264/H.265 视频帧序列
  `-- Audio Track：G711U/AAC 音频帧序列
```

但是每次调用 `on_stream_come()` 时，只会传入一种媒体数据：

```text
一次回调 = 一帧音频
或者
一次回调 = 一帧视频
```

回调函数通过 `head->type` 判断本次数据类型：

```cpp
if (head->type == STREAM_AUDIO_FRAME) {
    // 本次是音频。
    // 编码数据位于 buf + len。
} else {
    // 本次是视频。
    // 编码数据位于 head->nalu[]。
}
```

因此“一个通道包含音视频”的准确含义是：

> 同一个逻辑流下面注册了音频 Track 和视频 Track，两类帧共用一个分发入口，但分别产生回调。

---

## 2. 为什么音频和视频会交错回调

取流线程同时等待 VENC 和 AENC 的文件描述符：

```text
select(VENC fd, AENC fd)
```

当 AENC 可读时：

```text
AENC fd 可读
  -> get audio stream
  -> process_audio_stream()
  -> on_stream_come(AudioFrame)
```

当 VENC 可读时：

```text
VENC fd 可读
  -> ss_mpi_venc_get_stream()
  -> process_video_stream()
  -> on_stream_come(VideoFrame)
```

可能出现的回调顺序是：

```text
AudioFrame  PTS=1000 ms
VideoFrame  PTS=1000 ms
AudioFrame  PTS=1020 ms
AudioFrame  PTS=1040 ms
VideoFrame  PTS=1066 ms
```

音频和视频的帧率不同，因此不会严格按照“一帧音频、一帧视频”成对出现。

音视频同步依赖各自的 PTS，而不是依赖回调先后顺序。

---

## 3. 当前视频回调是否按帧对齐

是。

H.264 和 H.265 编码器都配置了：

```cpp
m_venc_chn_attr.venc_attr.is_by_frame = TD_TRUE;
```

这个配置表示 VENC 使用按帧取流模式，而不是按 Slice 单独取流。

因此一次：

```cpp
ss_mpi_venc_get_stream(venc_chn, &stream, TD_TRUE);
```

通常取得一张完整编码图像，也就是一个 Access Unit。

项目随后针对这次 `get_stream()` 只执行一次：

```cpp
post_stream_to_observer(...);
```

最终表现为：

```text
一张编码图像
  -> 一次 on_stream_come() 视频回调
  -> 一个 MediaFrame
```

---

## 4. 什么是编码帧或 Access Unit

摄像头产生的是原始图像帧，经过 VENC 后会变成编码图像。

从业务角度看：

```text
一张输入 YUV 图像
  -> 编码器处理
  -> 一张 H.264/H.265 编码图像
```

这一张完整的编码图像通常称为 Access Unit。

Access Unit 可以是：

- IDR/I 帧；
- P 帧；
- 如果启用 B 帧，也可能是 B 帧。

Access Unit 是业务层认为的“一帧”，但它内部不一定只有一块内存或一个 NALU。

---

## 5. 一帧内部为什么有多个 Pack

海思 `ss_mpi_venc_get_stream()` 返回：

```cpp
ot_venc_stream stream;
```

其中包含：

```cpp
stream.pack;
stream.pack_cnt;
```

项目首先查询当前编码帧需要多少个 Pack：

```cpp
ot_venc_chn_status status{};
ss_mpi_venc_query_status(venc_chn, &status);

stream.pack_cnt = status.cur_packs;
```

然后为这一帧准备 Pack 数组，再调用：

```cpp
ss_mpi_venc_get_stream(venc_chn, &stream, TD_TRUE);
```

层级关系是：

```text
一次 get_stream()
  `-- 一张编码图像
      |-- Pack 0
      |-- Pack 1
      `-- Pack 2
```

Pack 是海思 VENC 返回码流时使用的缓冲组织单位。

它不是业务层的一帧，也不能简单认为每个 Pack 必然对应一个完整视频帧。

---

## 6. Pack 和 NALU 的关系

H.264/H.265 码流由 NALU 组成。

项目遍历一帧中的所有 Pack：

```cpp
for (td_u32 i = 0; i < pstream->pack_cnt; ++i) {
    const auto& pack = pstream->pack[i];

    const td_u8* data = pack.addr + pack.offset;
    const td_u32 size = pack.len - pack.offset;
}
```

随后把有效数据整理进：

```cpp
head->nalu[];
head->nalu_count;
```

当前代码实际采用了比较直接的映射：

```text
一个有效 Pack
  -> 一个 nalu_t 记录
```

但从概念上要注意：

> Pack 是海思缓冲区组织方式，NALU 是 H.264/H.265 码流语法单位。它们属于不同层次，不能在所有配置和所有 SDK 模式下认为永远一一对应。

当前项目可以按现有实现阅读，但设计新封装时应以 SDK 对 `ot_venc_pack` 的正式定义为准。

---

## 7. P 帧通常是什么结构

普通 P 帧通常较小，可能类似：

```text
一次视频回调
  `-- 一个 P Frame Access Unit
      `-- P Slice NALU
```

如果编码器把一帧切成多个 Slice，也可能是：

```text
一次视频回调
  `-- 一个 P Frame Access Unit
      |-- P Slice 0
      |-- P Slice 1
      `-- P Slice 2
```

无论内部 Slice 数量是多少，在当前按帧模式下，业务层仍然只收到一次视频回调。

---

## 8. I 帧为什么更大

I 帧或 IDR 帧不依赖之前的预测帧，需要保存更多完整图像信息，因此一般明显大于 P 帧。

一个 H.264 IDR Access Unit 可能包含：

```text
一次视频回调
  `-- 一个 IDR Access Unit
      |-- SPS NALU
      |-- PPS NALU
      `-- IDR Slice NALU
```

如果编码器使用多个 Slice：

```text
一次视频回调
  `-- 一个 IDR Access Unit
      |-- SPS
      |-- PPS
      |-- IDR Slice 0
      |-- IDR Slice 1
      `-- IDR Slice 2
```

所以：

- I 帧可能包含更多 Pack；
- I 帧可能包含更多 NALU；
- 每个 NALU 也可能更大；
- 但当前配置下仍然是一张编码图像触发一次业务回调。

不会仅仅因为 I 帧很大，就自动变成多次 `on_stream_come()` 回调。

---

## 9. SPS、PPS、IDR 分别是什么

以 H.264 为例：

### SPS

Sequence Parameter Set，序列参数集。

包含解码整个视频序列所需的重要参数，例如分辨率、Profile 等信息。

### PPS

Picture Parameter Set，图像参数集。

包含图像级编码参数。

### IDR

Instantaneous Decoder Refresh，即时解码刷新帧。

解码器从 IDR 开始，可以不依赖 IDR 之前的图像。新观看者通常需要先取得：

```text
SPS + PPS + IDR
```

才能正确开始解码。

这也是项目维护 GOP Cache、并在新订阅者出现时请求关键帧的原因。

---

## 10. 一个视频回调如何变成 MediaFrame

`EncodedStreamChannel::on_stream_come()` 收到一次视频回调后，会遍历：

```cpp
head->nalu[0 ... nalu_count - 1]
```

然后构造 `EncodedFrameView`：

```cpp
frame_view.stream_id = sobj->stream_id();
frame_view.type = MediaType::Video;
frame_view.codec = Codec::H264; // 或 H265
frame_view.pts_ms = ...;
frame_view.chunks = 所有 NALU;
```

接着：

```cpp
auto frame = copy_encoded_frame(frame_view);
```

`copy_encoded_frame()` 会计算所有 NALU 的总大小：

```text
total = NALU 0 size
      + NALU 1 size
      + NALU 2 size
      + ...
```

然后分配一块连续的 `MediaFrame` 内存，并依次复制：

```text
MediaFrame payload
  |-- NALU 0 bytes
  |-- NALU 1 bytes
  `-- NALU 2 bytes
```

同时记录每个 NALU 在连续内存中的：

```cpp
offset
size
```

最终关系是：

```text
一次视频回调
  -> 一个 EncodedFrameView
  -> 一个 MediaFrame
```

因此业务层仍然保留清晰的帧边界。

---

## 11. 为什么必须在回调中深拷贝

`head->nalu[i].data` 最终指向海思 VENC 管理的缓冲区。

调用链是：

```text
ss_mpi_venc_get_stream()
  -> process_video_stream()
  -> on_stream_come()
  -> copy_encoded_frame()
  -> ss_mpi_venc_release_stream()
```

一旦调用：

```cpp
ss_mpi_venc_release_stream(venc_chn, &stream);
```

原来的 Pack/NALU 地址就不能继续使用。

因此：

```text
VENC 临时缓冲区
  -> 回调中深拷贝
  -> 应用拥有的 MediaFrame
```

这是正确的生命周期转换。

如果只保存 `nalu.data` 指针，等回调返回后异步发送，就会读取已经被 VENC 回收或重新使用的内存。

---

## 12. get_stream 和 release_stream 必须成对

正确模式：

```cpp
if (ss_mpi_venc_get_stream(venc_chn, &stream, TD_TRUE) == TD_SUCCESS) {
    // 在此期间读取或复制 stream.pack 中的数据。

    ss_mpi_venc_release_stream(venc_chn, &stream);
}
```

无论后续写文件、复制或业务处理是否成功，只要 `get_stream()` 成功，就必须调用 `release_stream()`。

忘记释放会导致：

```text
VENC 缓冲无法回收
  -> 可用缓冲越来越少
  -> 编码器无法继续输出
```

这不仅是普通内存泄漏，而是会直接破坏实时视频流水线。

---

## 13. MediaSource 收到的是什么

`MediaSource::publish()` 每次收到一个完整的 `MediaFrame`：

```cpp
media_source_->publish(frame);
```

对于视频：

```text
一个 MediaFrame = 一张完整编码图像
```

它可能是：

- 一个 P Frame；
- 一个 IDR Frame；
- 内部带有 SPS/PPS/IDR 等多个 NALU。

`MediaSource` 不会把同一张编码图像拆成多个业务帧。

视频 `MediaFrame` 还会进入 GOP Cache：

```cpp
cache->push(frame);
```

订阅者收到的也仍然是这个完整帧对象。

---

## 14. RTP 分片是另一个层次

编码回调按帧对齐，不代表一帧只需要一个网络包。

网络有 MTU 限制。以太网常见 MTU 大约是 1500 字节，扣除 IP、UDP 和 RTP 头部后，一个 RTP 包能携带的视频负载更少。

一个较大的 IDR NALU 可能有几十 KB，甚至更大，不可能放进一个 RTP 包。

因此网络发送层还会分片：

```text
一个 MediaFrame
  `-- 一个很大的 IDR NALU
      |-- RTP packet 1
      |-- RTP packet 2
      |-- RTP packet 3
      |-- ...
      `-- RTP packet N
```

H.264 常使用 FU-A 等 RTP 分片方式，将一个大 NALU 拆成多个 RTP 包。

接收端会根据 RTP 头和 FU-A 信息重新组装 NALU，然后再交给解码器。

所以要明确区分：

```text
编码帧边界 != NALU 边界 != RTP 包边界
```

---

## 15. 四层边界对照

### 第一层：编码图像帧

业务和解码时间轴上的一张图像：

```text
IDR Frame / P Frame / B Frame
```

当前项目一次视频回调对应这一层的一帧。

### 第二层：VENC Pack

海思编码器返回数据时使用的缓冲组织单位：

```text
ot_venc_pack
```

一帧可以包含多个 Pack。

### 第三层：NALU

H.264/H.265 的码流语法单位：

```text
SPS / PPS / IDR Slice / P Slice / SEI ...
```

一帧可以包含多个 NALU。

### 第四层：RTP Packet

网络传输单位：

```text
RTP packet
```

一个大 NALU可以拆成多个 RTP 包。

综合起来：

```text
一次视频回调
`-- 一个编码帧 / Access Unit
    |-- 一个或多个 VENC Pack
    |-- 一个或多个 NALU
    `-- 每个大 NALU 可能拆成多个 RTP Packet
```

---

## 16. I 帧大的时候，程序的实际行为

假设某个 P 帧大小为 8 KB：

```text
一次 VENC get_stream
  -> 一次视频回调
  -> 一个 8 KB MediaFrame
  -> 若干 RTP 包
```

假设某个 IDR 帧大小为 100 KB，并包含 SPS、PPS 和 IDR Slice：

```text
一次 VENC get_stream
  -> 得到多个 Pack/NALU
  -> 一次视频回调
  -> 一个 100 KB MediaFrame
  -> 大量 RTP 包
```

变化的是：

- Pack 数量可能增加；
- NALU 数量可能增加；
- `MediaFrame` payload 变大；
- RTP 包数量明显增加；
- 瞬时网络带宽更高。

不变的是：

- 当前按帧模式下一张编码图像仍对应一次视频回调；
- 业务层仍然只创建一个 `MediaFrame`。

---

## 17. 需要注意的当前实现限制

项目定义：

```cpp
#define MAX_STREAM_NALU_COUNT 8
```

处理代码最多记录 8 个 NALU：

```cpp
for (td_u32 i = 0;
     i < pstream->pack_cnt &&
     sh.nalu_count < MAX_STREAM_NALU_COUNT;
     ++i) {
    ...
}
```

这意味着如果一次编码帧实际产生超过 8 个需要保留的 Pack/NALU，后面的数据不会被加入 `stream_head`。

当前普通编码配置下可能一直不会触发这个限制，但在以下场景需要重新评估：

- Slice 数量增加；
- 编码器输出额外 SEI；
- 更复杂的 H.264/H.265 参数集；
- SDK 的 Pack 组织方式变化；
- 高分辨率或特殊编码模式。

更稳妥的生产设计通常应使用动态容器，或者完整遍历 SDK 描述的每个 Pack 内部数据，而不是固定上限为 8。

---

## 18. 怎样判断一帧是不是关键帧

项目会检查 NALU 类型。

H.264 中：

```text
NALU type 5 = IDR Slice
```

因此只要这一帧的任一 NALU 是 type 5，就把整个 `MediaFrame` 标记为关键帧。

H.265 中常见关键图像类型包括：

```text
19 / 20 / 21
```

关键帧判断作用于整个编码帧，而不是说只有 IDR NALU 自己构成一个独立业务帧。

---

## 19. 最终记忆模型

先记住音视频回调：

```text
同一个 stream_id
  |-- 音频帧：单独回调
  `-- 视频帧：单独回调
```

再记住视频内部层次：

```text
一次视频回调
  `-- 一张完整编码图像
      |-- 多个 Pack
      |-- 多个 NALU
      `-- 网络层再拆成多个 RTP 包
```

最后记住生命周期：

```text
get_stream
  -> 在回调期间读取/深拷贝
  -> 创建应用自己的 MediaFrame
  -> release_stream
  -> MediaSource/WebRTC 可以异步使用 MediaFrame
```

一句话总结：

> 当前项目按编码帧回调；一帧可以由多个 Pack 和 NALU 组成，I 帧即使很大也仍然只产生一个业务视频回调，之后在 RTP 网络层才会继续拆包。
